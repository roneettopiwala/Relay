## Investigating an anomaly: workers=4, concurrency=10

The three runs above for this configuration are inconsistent (22.41, 15.78, 6.92
tasks/sec) while every other configuration is tightly clustered. Rather than
average three noisy numbers and call it done, re-ran the same configuration 5
more times:

| Run | Throughput (tasks/s) | E2E P50 |
|---|---|---|
| 1 | 6.92 | 14.32s |
| 2 | 6.96 | 14.48s |
| 3 | 6.94 | 14.46s |
| 4 | 6.95 | 14.62s |
| 5 | 7.00 | 14.40s |

Tightly clustered at ~6.9-7.0 — matching run 3 of the original set and matching
`workers=4` at every other concurrency tested. **Conclusion: the first two
original runs (22.41, 15.78) were transient anomalies**, most likely lower
background load on this shared dev machine during those specific runs, not a
real difference in Relay's behavior at low concurrency. The corrected,
trustworthy figure for `workers=4` is ~6.9 tasks/sec — used below instead of a
naive average of the original three.

## Summary

| Workers | Steady-state throughput | E2E P50 | E2E P99 | Peak busy |
|---|---|---|---|---|
| 4 | ~6.9 tasks/s | ~14.6s | ~28.9s | 4 (always exact) |
| 8 | ~8.5 tasks/s | ~12.1s | ~23.3s | 8 (always exact) |

**Peak worker utilization matched the configured worker count exactly across
all 18 runs and every re-run** — the concurrency-safety guarantee this whole
project is built on held under every load shape tested, including bursts of
100 concurrent submitters against 4 workers.

**Scaling is sub-linear**: doubling workers (4→8) gained ~23% throughput
(6.9→8.5 tasks/s), not 2x. Back-calculating average per-task wall time
(workers ÷ throughput): ~580ms/task at 4 workers, ~940ms/task at 8 workers —
each individual task got *slower*, not faster, when more of them ran at once.
This points at resource contention, not a Relay bottleneck: this is a shared
8-core dev laptop (not an isolated benchmark box, noted above), and 8
concurrent Docker containers compete harder for the same CPU/IO than 4 do.
`peak_busy` staying exactly correct throughout confirms the *scheduling* is
right; the *execution* cost per task is what's constrained by the host. On
dedicated hardware with real spare capacity, this would be expected to scale
closer to linear. Quantifying how much of that ~580-940ms is Docker's own
container-start overhead vs. Relay's own added overhead (HTTP + queue +
dispatch) is exactly what Checkpoint 2 (Relay vs. raw execution) measures
next.

**The deep end-to-end latency numbers (P50 ~12-15s, P99 ~23-29s) are a queueing
artifact, not per-task slowness**: N=200 tasks submitted in a near-instant
burst against only 4-8 workers means a task near the back of the queue
legitimately waits many seconds just to *start* — the same effect documented
in Phase 1's original load test. Submit latency (the time the *caller* actually
waits) stayed in single-digit milliseconds throughout (P50 well under 10ms in
every configuration) — confirming Submit truly never blocks on worker
availability, exactly as designed back in Phase 1.
